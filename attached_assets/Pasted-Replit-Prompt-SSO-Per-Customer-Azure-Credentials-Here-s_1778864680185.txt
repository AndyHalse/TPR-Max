Replit Prompt — SSO Per-Customer Azure Credentials
Here's the prompt, ready to hand to your developer:

PROMPT: Move SSO credentials from server environment variables to per-customer company settings

Context

TPR Max has Microsoft Azure Entra SSO built and working (server/ssoService.ts, server/routes/sso.ts, client/src/pages/settings/SsoSettings.tsx). The problem is that the Azure app credentials — AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, and AZURE_REDIRECT_URI — are currently read from server environment variables. This means every customer on the platform shares a single Azure app registration. That's wrong: enterprise customers each have their own Azure tenant, so each customer needs their own credentials stored in their company settings.

What needs to change

1. Database — add four new fields to the company settings table

Add these four columns (all nullable strings, default null):

ssoTenantId        VARCHAR
ssoClientId        VARCHAR
ssoClientSecret    VARCHAR (encrypt at rest using server/utils/encryption.ts)
ssoRedirectUri     VARCHAR
2. server/ssoService.ts — remove env var reads, accept credentials as parameters

Currently the service reads process.env.AZURE_TENANT_ID etc. at module level. Change every function that needs credentials to accept them as arguments instead:

// BEFORE:
export function isSsoConfigured(): boolean {
  return !!(process.env.AZURE_TENANT_ID && process.env.AZURE_CLIENT_ID && process.env.AZURE_CLIENT_SECRET);
}

// AFTER:
export function isSsoConfigured(settings: { ssoTenantId?: string; ssoClientId?: string; ssoClientSecret?: string }): boolean {
  return !!(settings.ssoTenantId && settings.ssoClientId && settings.ssoClientSecret);
}
Apply the same pattern to buildAuthUrl(), handleCallback(), and getDiscoveryUrl() — each must receive the customer's credentials from company settings, not read from env vars.

3. server/routes/sso.ts — look up the customer's settings before calling ssoService

In GET /api/auth/sso/check, GET /api/auth/sso/start, and the callback handler:

Identify the customer from the request (company name on /check, session on /start and callback)
Load that customer's company settings from the database
Pass settings.ssoTenantId, settings.ssoClientId, settings.ssoClientSecret, settings.ssoRedirectUri into the ssoService functions
Decrypt ssoClientSecret using server/utils/encryption.ts before passing it in
4. client/src/pages/settings/SsoSettings.tsx — add credential input fields

The current UI shows a "configured / not configured" badge read from the server. Add four input fields below the existing SSO login mode dropdown:

Azure Tenant ID — text input, placeholder: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
Application (Client) ID — text input, placeholder: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
Client Secret — password input (masked), placeholder: Enter Azure app client secret
Redirect URI — text input, pre-filled with https://[their-domain]/api/auth/sso/callback
Add a Save button that POSTs to a new endpoint PUT /api/settings/sso-credentials. The status badge should reflect whether this customer's credentials are configured, not the server env vars.

5. Create PUT /api/settings/sso-credentials endpoint

This endpoint should:

Require admin authentication
Accept { ssoTenantId, ssoClientId, ssoClientSecret, ssoRedirectUri }
Encrypt ssoClientSecret using server/utils/encryption.ts before saving
Save all four fields to the customer's company settings row
Return the updated SSO status (configured true/false)
6. Remove the env var dependency entirely

Once all routes are reading from customer settings, remove AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET, and AZURE_REDIRECT_URI from .env.example and any documentation. They should no longer be needed at runtime.

What not to change

Do not change the OIDC flow itself (buildAuthUrl, handleCallback — logic stays the same, just the credential source changes)
Do not change how the SSO login modes (standard / both / sso_only) work
Do not change the auto-provision or default role logic
Test

After the change, two different customers should be able to configure different Azure tenants in their own settings pages, and each should authenticate against their own Azure app — completely independently, with no server restart required.
