
Replit Prompt — Audit & Inspection Engine
What we're building
A new module called the Audit & Inspection Engine at route /audits.

This module lets users create inspection templates, schedule and conduct inspections across different categories (safety, fire, environmental, vehicle, housekeeping, etc.), record findings with photo evidence, assign corrective actions, and track closure. Think of it as the inspection and audit layer that sits on top of everything TPR Max already manages.

This is a large module. It has the same structural complexity as PPM — it's multi-tab, it has templates, it has live records, and it has a mobile completion flow. Build it in the same style as PPM throughout.

Codebase context
TypeScript full-stack application:

Server: Express.js, Drizzle ORM, PostgreSQL (isolated per-customer schema)
Client: React, Wouter routing, TanStack Query, Tailwind CSS, shadcn/ui, Lucide icons
Auth: requireAuth middleware, req.customerId on all authenticated requests
Customer DB pattern: const context = simpleDatabaseService.createCustomerContext(req.user!.username, req.customerId) then const custDb = await customerDbService.getCustomerDatabase(context.customerId)
Schema file: server/isolatedSchema.ts — all new tables go here
Routes file: server/routes/index.ts — all new route registrations go here

Feature gates: Follow the requirePPMFeature pattern in server/routes/ppm.ts (lines 65–78) for the feature gate middleware
Follow patterns from:

Server routes: server/routes/ppm.ts (structure, error handling, auth patterns, DB queries)
Client page structure: client/src/pages/PPM.tsx (tab layout, GlassCard use, mutation patterns, form patterns)

Step 2 — Server routes
Create server/routes/auditEngine.ts. Export registerAuditEngineRoutes(app: Express).

Add a feature gate middleware at the top of the file, exactly like the requirePPMFeature pattern in ppm.ts:

const requireAuditFeature = async (req: any, res: any, next: any) => {
  try {
    const context = simpleDatabaseService.createCustomerContext(req.user!.username, req.customerId);
    const settings = await simpleDatabaseService.getCompanySettings(context);
    if (!settings?.featureAuditEngine) {
      return res.status(403).json({ error: 'Audit & Inspection module is not enabled for your account.' });
    }
    next();
  } catch (error) { next(error); }
};
Apply requireAuditFeature after requireAuth on all /api/audits/* routes.

Templates CRUD
GET    /api/audits/templates              — list all templates
POST   /api/audits/templates              — create template (with items array in body)
GET    /api/audits/templates/:id          — get single template with its items
PUT    /api/audits/templates/:id          — update template metadata
DELETE /api/audits/templates/:id          — delete template (cascades to items)
GET    /api/audits/templates/:id/items    — list items for a template
POST   /api/audits/templates/:id/items    — add item to template
PUT    /api/audits/templates/:id/items/:itemId  — update item
DELETE /api/audits/templates/:id/items/:itemId  — delete item
When creating a template via POST /api/audits/templates, the body may include an items array. Insert the template first, then insert all items with templateId set and sortOrder based on array index.

Records CRUD
GET    /api/audits/records                — list all audit records (with summary data)
POST   /api/audits/records                — create new audit record (schedules it)
GET    /api/audits/records/:id            — get single audit with all items and corrective actions
PUT    /api/audits/records/:id            — update record metadata
DELETE /api/audits/records/:id            — delete record
POST   /api/audits/records/:id/start      — set status = in_progress, create auditRecordItems from template
POST   /api/audits/records/:id/submit     — calculate score, set status = completed, set conductedAt
GET    /api/audits/records/:id/token      — generate/refresh mobile access token (same pattern as PPM work order token)
Score calculation in POST /api/audits/records/:id/submit:

passCount = items where response = 'pass'
failCount = items where response = 'fail'
naCount   = items where response = 'na'
scoreable = passCount + failCount   // na items don't count toward total
score     = scoreable > 0 ? Math.round((passCount / scoreable) * 100) : 100
If any item where isCritical = true has response = 'fail', set passed = false regardless of score.
Otherwise passed = score >= template.passScore.

Set overallScore, passed, conductedAt = new Date(), status = 'completed'.

Corrective Actions CRUD
GET    /api/audits/records/:id/actions    — list corrective actions for an audit
POST   /api/audits/records/:id/actions    — create corrective action
PUT    /api/audits/actions/:id            — update action (status, assignee, closure notes, etc.)
DELETE /api/audits/actions/:id            — delete action
POST   /api/audits/actions/:id/close      — close action: set status = completed, closedAt, closedBy
Record items (for live audit completion)
PUT    /api/audits/records/:id/items/:itemId   — update a single item response, note, photoUrl
This is used during audit completion — the user marks each item as pass/fail/na and optionally adds a note or photo.

Mobile public endpoint (no auth required)
GET    /api/audits/public/:token          — get audit record with items (no login required)
PUT    /api/audits/public/:token          — update item responses during mobile completion
POST   /api/audits/public/:token/submit   — submit the completed audit
Rate-limit this endpoint at 60 requests per minute per IP. Validate the token against auditRecords.accessToken and check accessTokenExpiresAt. Tokens expire after 7 days.

Dashboard summary
GET    /api/audits/summary
Returns:

{
  totalScheduled: number,
  overdueCount: number,
  completedThisMonth: number,
  openActions: number,
  overdueActions: number,
  passRate: number,             // % of completed audits that passed, last 90 days
  recentAudits: AuditRecord[],  // Last 10 completed
  upcomingAudits: AuditRecord[] // Next 10 scheduled
}
Cron job
Register a daily cron (at 08:00 Europe/London, same pattern as the PPM overdue cron) that:

Finds all auditRecords where status = 'scheduled' and scheduledDate < today and overdueAlertedAt IS NULL — mark them status = 'overdue' and set overdueAlertedAt = now()
Finds all auditCorrectiveActions where status = 'open' OR status = 'in_progress' and dueDate < today — mark them status = 'overdue'
No email notifications required for this first build. Just status updates.

Important implementation notes
Checklist builder state. The template creation form manages checklist items as local React state — an array of objects. Each item has a temporary id (use crypto.randomUUID() locally) for React key purposes. On save, strip the local ids and POST the full items array. On edit, load items from GET /api/audits/templates/:id and populate local state.
Auto-save during audit. When a user is conducting an audit and clicks pass/fail/na on an item, immediately fire PUT /api/audits/records/:id/items/:itemId. Don't wait for a form submit. This prevents data loss if the browser closes. Show a small "Saving…" indicator.
Score calculation is server-side only. The client shows the score returned from POST /api/audits/records/:id/submit. Don't calculate the score on the client — calculate it in the server endpoint and return it.
Critical item failure. If an item with isCritical = true is marked as fail, show a red warning banner: "This is a critical item. Failing a critical check will result in an overall audit failure regardless of score." This is informational only — don't prevent them marking it as fail.
Mobile token generation. Follow the exact pattern used for PPM work order tokens in ppm.ts. Generate a random hex token with randomBytes(24).toString('hex'). Store in auditRecords.accessToken. Set accessTokenExpiresAt to 7 days from now.
Category badges. Use consistent colours throughout:
Safety = blue
Fire = red/orange
Environmental = green
Vehicle = purple
Housekeeping = amber
Behavioural = teal
Custom = grey
Corrective action email (future — not this build). The assignedEmail field is captured now so email notifications can be wired up later. For this build, no emails are sent — just store the data.
Audit record creation from the Overview tab. The "Schedule New Audit" button on the Overview tab should open the same "Create Audit Record" dialog as the one in the Records tab. Reuse the same component.
Error handling. If any query fails, return a proper JSON error with status 500 and a clear message. Log with logger.error(). Don't let unhandled errors crash the route.
TypeScript. No any types except where using the Drizzle custDb instance (that one is unavoidable — use as any only for the custDb itself as per existing patterns). All interfaces defined at the top of the client file, all types exported from the schema.
