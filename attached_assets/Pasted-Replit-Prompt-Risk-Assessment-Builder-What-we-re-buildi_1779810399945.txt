Replit Prompt — Risk Assessment Builder
What we're building
A new module called the Risk Assessment Builder at route /ra-builder.

This is an authoring tool — not a document upload system. The existing RAMS module already handles uploading, tracking, approving, and version-controlling PDF/Word RAMS documents that contractors submit. This is the complementary tool that lets users write risk assessments directly inside TPR Max, with structured hazard rows, risk scoring, and AI-suggested control measures.

When a risk assessment is completed and approved in the builder, it automatically creates a record in the existing RAMS document register (ramsDocuments table), completing the full lifecycle: author → review → approve → RAMS library.

Six assessment types are supported: General, COSHH, Manual Handling, Working at Height, Lone Working, DSE.

Codebase context
TypeScript full-stack application:

Server: Express.js, Drizzle ORM, PostgreSQL (isolated per-customer schema)
Client: React, Wouter routing, TanStack Query, Tailwind CSS, shadcn/ui, Lucide icons
Auth: requireAuth middleware, req.customerId on authenticated requests
Customer DB pattern: const context = simpleDatabaseService.createCustomerContext(req.user!.username, req.customerId) → const custDb = await customerDbService.getCustomerDatabase(context.customerId)

raBuilderAssessments
export const raBuilderAssessments = pgTable("ra_builder_assessments", {
  id: varchar("id").primaryKey().default(sql`gen_random_uuid()`),
  title: text("title").notNull(),
  raType: text("ra_type").notNull().default("general"),
  // raType values: general | coshh | manual_handling | working_at_height | lone_working | dse
  status: text("status").notNull().default("draft"),
  // status values: draft | review | approved | archived
  taskDescription: text("task_description"),
  location: text("location"),
  department: text("department"),
  preparedBy: text("prepared_by"),
  reviewedBy: text("reviewed_by"),
  approvedBy: text("approved_by"),
  assessmentDate: text("assessment_date"),       // ISO date YYYY-MM-DD
  nextReviewDate: text("next_review_date"),       // ISO date YYYY-MM-DD
  // Type-specific metadata — stored as JSON text
  // General: {} (no extra fields)
  // COSHH: { substanceName, casNumber, sdsRef, form, exposureRoutes[], welReference, quantity, frequency }
  // Manual Handling: { loadDescription, approxWeightKg, dimensions, frequency, distanceCarried, postureIssues }
  // Working at Height: { maxHeightMetres, accessEquipment, surfaceType, rescuePlan }
  // Lone Working: { workLocation, workDuration, checkInIntervalMins, emergencyContactName, emergencyContactPhone, communicationMethod }
  // DSE: { assesseeName, workstationLocation, displayType, seatingNotes, keyboardMouse, lighting, environment, eyeTestStatus }
  typeMetadata: text("type_metadata").default("{}"),
  notes: text("notes"),
  // Link back to the RAMS document created on approval
  linkedRamsDocumentId: varchar("linked_rams_document_id"),
  createdAt: timestamp("created_at").defaultNow(),
  updatedAt: timestamp("updated_at").defaultNow(),
});

export const insertRaBuilderAssessmentSchema = createInsertSchema(raBuilderAssessments).omit({ id: true, createdAt: true, updatedAt: true });
export type InsertRaBuilderAssessment = z.infer<typeof insertRaBuilderAssessmentSchema>;
export type RaBuilderAssessment = typeof raBuilderAssessments.$inferSelect;

Step 2 — Server routes

Add a feature gate at the top (exactly like the requirePPMFeature pattern in ppm.ts):

const requireRaBuilderFeature = async (req: any, res: any, next: any) => {
  try {
    const context = simpleDatabaseService.createCustomerContext(req.user!.username, req.customerId);
    const settings = await simpleDatabaseService.getCompanySettings(context);
    if (!settings?.featureRaBuilder) {
      return res.status(403).json({ error: 'Risk Assessment Builder is not enabled for your account.' });
    }
    next();
  } catch (error) { next(error); }
};

POST   /api/ra-builder/assessments/:id/approve  — set status = approved, set approvedAt
POST   /api/ra-builder/assessments/:id/archive  — set status = archived
POST /api/ra-builder/assessments/:id/approve — this endpoint does three things:

Sets status = 'approved', approvedBy = req.user.username
Creates a new record in the ramsDocuments table (in isolatedSchema) automatically:
documentName = assessment title + " (RA Builder)"
ramsIdRef = "RA-" + first 8 chars of assessment id
documentUrl = /ra-builder/assessments/${id}/print (a link to the print view)
expiryDate = nextReviewDate from the assessment (or 12 months from now if not set)
status = 'valid'
workCategory = the raType value (map: general→general, working_at_height→working_at_height, etc.)
jobDescription = taskDescription
siteLocation = location
Sets linkedRamsDocumentId on the assessment to the new RAMS document id
Returns the updated assessment
Hazards CRUD
GET    /api/ra-builder/assessments/:id/hazards           — list hazards for this assessment (ordered by sortOrder)
POST   /api/ra-builder/assessments/:id/hazards           — add a hazard row
PUT    /api/ra-builder/assessments/:id/hazards/:hazardId — update hazard
DELETE /api/ra-builder/assessments/:id/hazards/:hazardId — delete hazard
POST   /api/ra-builder/assessments/:id/hazards/reorder   — update sortOrder for all hazards (body: array of { id, sortOrder })
For POST and PUT hazard routes, automatically calculate riskRating = likelihood * severity and residualRiskRating = residualLikelihood * residualSeverity server-side before saving.

AI suggest controls
POST   /api/ra-builder/suggest-controls
Body:

{
  raType: string,           // "general" | "coshh" | etc.
  hazardDescription: string,
  taskDescription?: string,
  existingControls?: string
}
This endpoint:

Checks the customer has a Claude API key in customerApiKeys where serviceType = 'claude' and status = 'active'
If no key found, returns { error: 'no_api_key', message: 'No Claude API key configured in Settings > AI' }
Decrypts the key with decryptData(row.encryptedKey, row.initializationVector, row.authTag || '')
Calls Claude with claude-3-5-sonnet-20241022, max_tokens 512
System prompt:

You are a UK Health & Safety compliance expert. Given a hazard description and task context, suggest practical control measures based on the hierarchy of controls: Elimination, Substitution, Engineering Controls, Administrative Controls, PPE. Return ONLY a JSON array of control measure strings. No markdown, no explanation, no numbering. Return 4–6 specific, practical suggestions.
User message:

Assessment type: ${raType}
Task: ${taskDescription || 'Not specified'}
Hazard: ${hazardDescription}
Existing controls already in place: ${existingControls || 'None stated'}
Suggest additional control measures.
Parse the JSON array from the response, stripping any markdown fences
Return { suggestions: string[] }
If the Claude call fails or the API key is invalid, return { error: 'ai_failed', message: string } — never throw a 500 for AI failures.

Important implementation notes
Risk rating is always calculated server-side. On POST and PUT to hazard endpoints, calculate riskRating = likelihood * severity and residualRiskRating = residualLikelihood * residualSeverity. Never trust the client-supplied value.
Auto-save debounce. On the editor page, every field change should trigger a debounced save (800ms). Use useRef to hold the debounce timer. Only auto-save if the assessment already has an id (i.e. it's been created). For a brand new assessment, create it on first explicit "Save Draft" click. After creation, auto-save takes over.
Type metadata is JSON. Store and retrieve typeMetadata as a JSON string. Parse it on load (JSON.parse(assessment.typeMetadata || '{}')), merge field changes into the parsed object, stringify on save. Do not use separate columns for each type's fields.
AI suggestions are additive. When a user clicks a suggestion chip, append it to the existing additionalControls text — don't replace it. Add a newline separator if text already exists.
No AI key = graceful degradation. If no Claude API key is configured, the AI Suggest button should be disabled (not hidden), with the tooltip making it clear why. Show opacity-50 cursor-not-allowed on the button.
RAMS link on approval. The ramsDocuments table uses customerId (see shared/schema.ts line 1569). When creating the RAMS record on approval, use the customer context customerId. The ramsDocuments in isolatedSchema.ts does not have a customerId column — use whichever schema the customer's RAMS data is stored in. If the isolated schema version is used (the simpler one at isolatedSchema.ts line 1053), use custDb to insert. Check which one RAMSManagement.tsx queries — it uses /api/rams which is in server/routes/rams.ts. Look at how that route stores data to confirm which table and schema to write to.
No drag-and-drop required. Up/down arrow reordering is sufficient and much simpler to build correctly.
Print view. The print layout does not need to be beautiful — it needs to be complete and professional. A clean two-column header (company logo + document reference), followed by type-specific metadata section if applicable, then a proper hazard table with all columns, then the sign-off block.
TypeScript. All interfaces defined at top of the client file. Types exported from schema. No loose any except the custDb instance.
Error handling. Catch all errors in every route handler. Log with logger.error(). Return clean JSON errors.

The key thing to flag to your developer, Andy: the auto-save is non-negotiable. A risk assessment can have 10–15 hazard rows and take 30 minutes to complete. Without auto-save, one accidental browser navigation destroys all that work. The debounce pattern is straightforward — useRef timer, clear and reset on every change, fire the PUT after 800ms of no changes.

The AI suggest button is the other feature worth testing carefully — specifically the graceful degradation when there's no Claude key, since not every customer will have one configured yet.
